# Міні-банк / P2P-платформа — концепція та план

Систематизація ідеї: багатокористувацька платформа, де **інвестори** тримають кошти
й дають їх у користування, а **бізнеси** беруть ці кошти в борг за оголошену ставку.
Замінює/поглинає поточний однокористувацький трекер (`APP_CONCEPT.md`).

---

## 0. Зафіксовані рішення

Підтверджено. Далі весь план виходить саме з цього.

| # | Рішення | Наслідок для архітектури |
|---|---|---|
| D1 | **Гроші віртуальні** — внутрішній реєстр, реальних платіжних рейок немає. Поповнення/виведення = операція адміна | Немає KYC/PSP/AML. Але реєстр робимо «по-справжньому» (§2), щоб підключення реальних рейок пізніше не переписувало ядро |
| D2 | **Дефолт ігноруємо на цьому етапі** | Стани `OVERDUE`/`DEFAULTED` є в моделі, але без логіки стягнення, резервного фонду й впливу на скоринг. Відкладено у Ф6 |
| D3 | **Дохід платформи:** комісія з переказів + частка з відсоткового доходу інвестора + FX-спред | Потрібен окремий шар `fee_policy` (§2.4), інакше комісії розповзуться по коду |
| D4 | **Синдикація одразу** — кілька інвесторів в одну позику | `loan_shares` + `repayment_splits` з першого дня (§6) |
| D5 | **Міграції даних немає** — поточна БД переписується з нуля | Можна проєктувати схему чисто, без сумісності зі `snapshots` |
| D6 | **Формат курсу від майбутнього API:** `{ CODE, BID, SELL }` | Інтерфейс провайдера фіксовано (§3.3) |
| D7 | Ролі на старті взаємовиключні, модель одразу під «і те, і те» | `user.capabilities`, не `user.role` |
| D8 | Базова валюта звітності — UAH, одна юрисдикція | Всі агрегати рахуються в UAH за курсом на дату |

> По D7: у БД **не** робити `user.role` як enum. Робити
> `user.capabilities = ['invest'] | ['borrow'] | ['invest','borrow']`. При реєстрації
> користувач обирає одне — але розширення до обох це просто додавання елемента в
> масив, без міграції та без переписування перевірок доступу.

> По D1: єдине, що дає віртуальність — **не робимо** інтеграцій, верифікації особи
> й лімітів регулятора. Подвійний запис, ідемпотентність і звірку робимо все одно —
> вони коштують дешево зараз і рятують від нерозв'язних багів потім.

> По D2: важливо, що ігнорування дефолту — це **не** «позика не може прострочитись».
> Дата платежу все одно порівнюється з поточною, статус `OVERDUE` виставляється й
> видно в UI. Просто немає наслідків: ні штрафів, ні списань, ні падіння рейтингу.

## 1. Ролі

**Investor (звичайний користувач)**
- Має гаманці в кількох валютах
- Переказує кошти іншим користувачам (з коментарем)
- Конвертує валюту за курсом платформи
- Переглядає заявки бізнесів і фінансує ті, що підходять
- Бачить портфель: скільки вкладено, під який %, скільки повернуто, дохідність

**Business (бізнесмен / позичальник)**
- Має гаманці + **каси** (фізичні точки обліку готівки — успадковано з поточної моделі)
- Задає стартовий капітал (baseline для P&L)
- Виставляє **заявки на залучення**: сума, валюта, ставка за користування, строк
- Отримує кошти, обслуговує графік виплат, погашає тіло
- Бачить вартість капіталу і власний P&L (це, по суті, поточний движок `engine.js`)

**Admin**
- Поповнення/виведення (за A1), модерація заявок і бізнесів, курси, спори, аудит

## 2. Гроші: як їх зберігати (найважливіше рішення)

Це фундамент — якщо тут помилитись, потім не полагодиш.

### 2.1 Подвійний запис (double-entry)

**Ніколи не зберігати баланс як число, яке ми UPDATE-имо.** Баланс — це завжди
похідна від суми проводок.

```
transactions        (id, type, status, created_at, idempotency_key, meta_json)
ledger_entries      (id, transaction_id, account_id, currency, amount /* signed */, created_at)
accounts            (id, owner_type, owner_id, kind, currency)
```

Інваріант: **сума всіх `amount` в межах однієї транзакції та однієї валюти = 0.**
Перевіряється в БД-констрейнті/тригері або в тесті на кожну транзакцію.
Це єдиний спосіб гарантувати, що гроші не з'являються з нізвідки.

Типи рахунків (`accounts.kind`):
- `user_wallet` — гаманець користувача в конкретній валюті
- `user_hold` — заморожені кошти (виставлена пропозиція фінансування, pending-переказ)
- `business_register` — каса бізнесу
- `loan_principal` — тіло конкретної позики
- `platform_fee` — комісія платформи
- `platform_fx` — результат спреду на конвертації
- `external` — контрагент для поповнення/виведення (щоб deposit теж був збалансований)

Баланс = `SELECT SUM(amount) FROM ledger_entries WHERE account_id = ?`.
Для швидкості — матеріалізована таблиця `account_balances`, яку оновлює
той самий тригер/транзакція, з періодичною звіркою (reconciliation job).

### 2.2 Формат сум

- **Тільки цілі числа в мінорних одиницях** (копійки/центи), тип `bigint`.
  Ніяких `float`. Ніяких `numeric` у бізнес-логіці JS.
- Кожна валюта має `exponent` (UAH/USD/EUR = 2, JPY = 0) — таблиця `currencies`.
- На клієнті — `decimal.js` (вже в залежностях) лише для відображення/вводу.

### 2.3 Ідемпотентність та конкурентність

- Кожен write-запит несе `Idempotency-Key` (UUID від клієнта). Унікальний індекс —
  повторний сабміт не створює другий переказ.
- Всі операції з грошима — в одній SQL-транзакції з `SELECT ... FOR UPDATE`
  на задіяних рахунках (або serializable isolation) — інакше подвійне списання.
- Проводки **immutable**. Скасування = зворотна транзакція (`reversal_of`), не DELETE.

### 2.4 Комісії (D3)

Три джерела доходу, і всі три — **звичайні проводки в тій самій транзакції**, а не
окремий процес. Комісія ніколи не списується другою транзакцією «потім»: інакше
буває стан, де переказ пройшов, а комісія — ні.

```
fee_policies (id, kind, currency, percent_bps, fixed_amount,
              min_amount, max_amount, effective_from, effective_to)
```

`kind`:
| kind | З кого | Коли | Орієнтир |
|---|---|---|---|
| `transfer` | відправник (або отримувач — налаштовується) | кожен переказ | 0.5%, мін. 1 грн, макс. 50 грн |
| `interest_share` | інвестор | з кожного отриманого % | 10% від суми відсотків |
| `fx_spread` | той, хто конвертує | кожна конвертація | закладений у BID/SELL, окремої проводки не потребує |
| `origination` (опційно) | бізнес | при видачі позики | 1% від тіла |

Приклад переказу 1000 UAH з комісією 0.5%:
```
sender_wallet(UAH)    -100500
recipient_wallet(UAH) +100000
platform_fee(UAH)        +500
```

Приклад платежу відсотків 200 UAH одному інвестору з часткою платформи 10%:
```
business_wallet(UAH)   -20000
investor_wallet(UAH)   +18000
platform_fee(UAH)       +2000
```

Правила, які варто закласти одразу:
- Політики **датовані** (`effective_from`) — зміна тарифу не переписує історію.
  Транзакція зберігає `fee_policy_id`, за яким її порахували.
- Комісія рахується **до** створення проводок і показується користувачу в
  підтвердженні («Спишеться 1005 грн, отримувач отримає 1000 грн»). Ніяких сюрпризів.
- Округлення комісії — завжди на користь платформи (`ceil`), але сума проводок
  все одно має сходитись у нуль; залишок від округлення йде на `platform_fee`.
- Нульова політика (0%) має бути валідною — щоб можна було вимкнути комісії
  конфігом на час тестування, не чіпаючи код.

## 3. Мультивалютність і курси (продуманий флоу)

Ти просив продумати перехід від хардкоду до API. Ключ — **абстракція постачальника
курсів + збереження котирувань як історичних фактів**.

### 3.1 Модель

```
currencies       (code PK, name, exponent, is_active)
rate_sources     (id, name, priority, is_active)         // 'hardcoded', 'nbu', 'openexchange'
exchange_rates   (id, source_id, base, quote, buy, sell, observed_at, expires_at)
fx_quotes        (id, user_id, from, to, amount_from, amount_to, rate_used,
                  spread_bps, expires_at, consumed_by_tx)
```

Курс **ніколи не читається з зовнішнього API в момент операції.** Фоновий job тягне
курси → пише в `exchange_rates`. Операція завжди читає з нашої БД. Це дає:
відтворюваність, стійкість до падіння провайдера, аудит («який курс був о 14:32»).

### 3.2 Флоу конвертації (quote-lock)

```
1. Користувач вводить: 1000 UAH → USD    (BID 40.00 / SELL 41.00)
2. POST /api/fx/quote → сервер бере актуальний rate, обирає потрібну сторону
   (користувач купує USD → застосовується SELL = 41.00),
   створює fx_quote з TTL 60 сек, повертає точні суми
3. UI показує: "Отримаєте 24.39 USD за курсом 41.00, дійсно 0:58"
4. POST /api/fx/execute { quote_id, idempotency_key }
5. Сервер перевіряє, що quote не протух і не використаний → одна транзакція:
      user_wallet(UAH)  -100000     // 1000.00 UAH
      platform_fx(UAH)  +100000
      platform_fx(USD)    -2439     // 24.39 USD
      user_wallet(USD)    +2439
```

Дохід платформи тут не окрема проводка — він «осідає» на парі рахунків
`platform_fx` як різниця між BID і SELL, і матеріалізується коли платформа
проводить зустрічну операцію. Для звітності рахується окремо:
`(mid − applied_rate) × amount`.

Округлення: результат конвертації завжди округлюється **вниз** для користувача
(`floor`), залишок — на `platform_fx`. Інакше на дрібних сумах система роздає
копійки з повітря.

Так користувач ніколи не отримує «курс змінився поки я тиснув кнопку», а платформа
не втрачає на волатильності.

### 3.3 Шлях від хардкоду до API (D6)

Формат відомий заздалегідь, тому інтерфейс провайдера фіксуємо одразу:

```
Rate = {
  code: 'USD',        // валюта, що котирується
  bid:  40.00,        // платформа КУПУЄ USD за 40 UAH → користувач продає USD по 40
  sell: 41.00,        // платформа ПРОДАЄ USD за 41 UAH → користувач купує USD по 41
}

RateProvider = {
  name: string,
  fetchRates(): Promise<Rate[]>
}
```

Нормалізація на вході: котирування завжди приводиться до пари `(base=UAH, quote=CODE)`,
`bid`/`sell` конвертуються в цілі числа (зберігати як `bigint` з фіксованим
масштабом, напр. 6 знаків → `40.00` = `40000000`). **Валідація обов'язкова:**
`sell > bid > 0`, і відхилення від попереднього значення не більше N% — інакше
одна битa відповідь API перекосить усі баланси. Підозріле котирування не
застосовується, а логується й алертиться.

- **Фаза 1:** `HardcodedRateProvider` — константи в
  `server/src/fx/providers/hardcoded.js`, повертає рівно такий самий `Rate[]`,
  пише в `exchange_rates` при старті/сіді.
- **Фаза 7:** твій API — новий файл, той самий інтерфейс, вмикається конфігом.
  Job раз на N хвилин. Fallback-ланцюжок за `rate_sources.priority`: якщо основний
  мовчить — беремо останній валідний курс і **позначаємо його як stale** в UI
  (це важливо для довіри).
- Код бізнес-логіки **не змінюється жодного рядка** — він і так читав з БД.

Спред (`sell − bid`) — це і є дохід платформи з FX (D3), окрема комісія не потрібна.
Середній курс `(bid + sell) / 2` використовується **тільки для звітності** (оцінка
портфеля в UAH), ніколи для реальної операції.

### 3.4 Курс і борг

Валюта позики фіксується при видачі. Платежі — в тій самій валюті. Якщо
позичальник хоче платити іншою — це спочатку конвертація (FX), потім платіж.
**Не змішувати** — інакше неможливо порахувати ні дохідність, ні прострочку.

## 4. Переказ між користувачами

```
POST /api/transfers { to_user, currency, amount, comment, idempotency_key }
```

- Пошук отримувача за username/email/handle (не за raw ID)
- **Коментар** до 280 символів + опційно теги/категорія — фільтр в історії
- Транзакція: `sender_wallet -X` / `recipient_wallet +X` (+ `platform_fee` якщо є комісія)
- Опційно: **запит коштів** (request money) — зворотний флоу, отримувач підтверджує
- Опційно: pending-переказ на неіснуючого користувача (кошти в `user_hold` до
  реєстрації або авто-повернення через 7 днів)

## 5. Каси, стартовий капітал і P&L бізнесу

Це місток до вже написаного — `engine.js` не викидається, а стає **per-business**.

```
businesses          (id, owner_user_id, name, base_currency, starting_capital,
                     starting_capital_currency, starting_at)
registers           (id, business_id, name, currency, is_active)
```

- Каса — це `account.kind = 'business_register'`. Готівкові рухи в касі — такі ж
  проводки, тому «скільки грн у касі 1» рахується тим самим способом.
- Стартовий капітал — **датована настройка** (не поле в снапшоті), як і планувалось
  у S5 серверного плану.
- Дашборд бізнесу = поточна формула з `APP_CALC.md`, але вхідні дані беруться з
  реєстру, а не з ручного вводу:
  ```
  Активи = Σ каси + Σ гаманці (в UAH за курсом)
  Зобов'язання = Σ непогашене тіло позик + нарахований, але не сплачений % 
  Чиста вартість = Активи − Зобов'язання
  P&L = Чиста вартість − Стартовий капітал
  Вартість капіталу = зважена середня ставка по активних позиках
  ```
- **Баг з `APP_CALC.md` §4 (E20) не переносити** — конвертація завжди від сумарного
  боргу по валюті, одна функція, покрита тестами.

## 6. Заявки та фінансування (ядро P2P)

Бізнес виставляє заявку → інвестори обирають. **Синдикація з першого дня** (D4):
одну заявку може закрити кілька інвесторів, кожен своєю сумою. Це різко підвищує
шанс, що заявка збереться, і його неможливо дешево додати пізніше — бо
синдикація змінює не UI, а спосіб, у який рахується кожне погашення.

### 6.1 Сутності

```
funding_requests (id, business_id, currency, amount_target, amount_funded,
                  rate_annual_bps, term_days, repayment_type, purpose, status,
                  min_ticket, expires_at, created_at)
fundings         (id, request_id, investor_id, amount, status, created_at)
loans            (id, request_id, business_id, currency, principal, rate_bps,
                  term_days, status, disbursed_at, matures_at)
loan_shares      (id, loan_id, investor_id, principal_share, share_bps)
repayments       (id, loan_id, due_at, principal_due, interest_due, status, paid_at)
repayment_splits (id, repayment_id, investor_id, principal, interest, fee)
```

### 6.2 Життєвий цикл

```
DRAFT → OPEN ──(зібрано 100% або дедлайн з min-fill)──→ FUNDED
  │                                                        │
  └──(дедлайн, не зібрано)──→ EXPIRED (холди знімаються)   ↓
                                                       DISBURSED (кошти в бізнесі)
                                                           ↓
                                    ┌── REPAYING ──→ CLOSED (все повернуто)
                                    └── OVERDUE ──→ DEFAULTED / RESTRUCTURED
                                                    └─ поза скоупом (D2)
```

За D2 гілка `DEFAULTED`/`RESTRUCTURED` існує в enum, але без логіки: прострочка
лише позначається статусом і видно в UI. Штрафи, списання, вплив на рейтинг —
у Ф6.

Ключове: коли інвестор натискає «профінансувати», кошти йдуть **не бізнесу
одразу**, а в `user_hold` (ескроу). Розморожуються або в бізнес (заявка зібралась),
або назад інвестору (заявка протухла). Без ескроу можлива ситуація, коли інвестор
вже витратив ті гроші, поки заявка збиралась.

### 6.3 Типи погашення (`repayment_type`)

- `bullet` — % щомісяця, тіло в кінці (найпростіше, з нього починати)
- `annuity` — рівні платежі
- `interest_only_flex` — тільки % , тіло за вимогою (найближче до «користування
  грошима» як ти описав — фактично револьверна лінія)

Раджу для MVP: **`bullet` + `interest_only_flex`**. Ануїтет — потім.

### 6.4 Ставка

Зберігати як `rate_annual_bps` (базисні пункти, ціле число) — річна ставка.
Показувати користувачу як завгодно («2% на місяць»), але рахувати в одному форматі,
інакше неможливо порівнювати заявки між собою.

Нарахування %: щоденний job нараховує `accrued_interest` (проводка
`loan_interest_accrued` → `investor_receivable`). Так % видно в реальному часі, а не
стрибком раз на місяць.

### 6.5 Розподіл платежу між інвесторами (наслідок D4)

Найбільш баг-схильне місце всієї системи. Правила:

- Частка інвестора фіксується **при видачі** як `share_bps` (базисні пункти від
  тіла), а не перераховується щоразу. Сума всіх `share_bps` = 10000 рівно.
- Кожен платіж бізнесу — **одна транзакція** з N+1 проводками (N інвесторів +
  комісія платформи). Не N окремих транзакцій: якщо третя впаде, система
  залишиться в неможливому стані.
- Округлення часток: рахуємо всі частки `floor`, залишок (`remainder`) віддаємо
  **найбільшій частці** (або першій за `id` — головне, детерміновано). Сума часток
  зобов'язана точно дорівнювати платежу.
- Часткова оплата: спочатку закриваються відсотки, потім тіло
  (`interest first`) — інакше дохідність інвестора рахується неправильно.

Приклад: бізнес платить 1000 UAH відсотків, інвестори A (60%) і B (40%),
частка платформи 10%:
```
business_wallet(UAH)   -100000
investor_A_wallet(UAH)  +54000   // 600.00 − 10%
investor_B_wallet(UAH)  +36000   // 400.00 − 10%
platform_fee(UAH)       +10000
```

### 6.6 Матчинг

- **MVP:** маркетплейс — список заявок з фільтрами (валюта, ставка, строк, рейтинг
  бізнесу), інвестор обирає вручну
- **Далі:** зустрічні пропозиції (інвестор каже «дам 50к під 18%», бізнес приймає)
- **Далі:** авто-інвестування за правилами (див. §11)

## 7. Рейтинг і статистика

Два **окремі** рейтинги — вони про різне.

**Рейтинг бізнесу (кредитоспроможність), 0–100:**
| Фактор | Вага |
|---|---|
| Частка платежів вчасно | 40% |
| Кількість закритих позик / загальний обсяг | 20% |
| Стаж на платформі | 10% |
| Поточне боргове навантаження (борг / активи) | 15% |
| Верифікація (документи, підтверджений бізнес) | 15% |
| **Штраф** за дефолт | −40 і «карантин» — *вмикається у Ф6 (D2)* |

Показувати як **літерний грейд** (A/B/C/D) + пояснення, а не голе число.
Обов'язково: рейтинг **не показувати як гарантію**, поруч завжди дисклеймер.

**Рейтинг/статистика інвестора:**
- Загальний обсяг, активний портфель, реалізована дохідність (XIRR), % дефолтів
- Рівні/бейджі (гейміфікація) — але **без** впливу на економіку, лише соціальне

**Статистика балансу (для всіх):**
- Графік балансу по днях, у розрізі валют і в базовій валюті
- Розбивка: гаманці / у позиках / заморожено / прострочено
- Cash-flow: вхідні, вихідні, %, комісії, FX-результат
- Експорт CSV

Технічно: щоденний job пише `balance_snapshots(user_id, date, currency, amount, kind)`
— так графік за рік це один індексований запит, а не агрегація мільйона проводок.
(Поточна таблиця `snapshots` еволюціонує саме в це.)

## 8. Безпека і цілісність

Без цього «міні-банк» — це іграшка з дірками.

- **Auth:** email+пароль (argon2), сесії в httpOnly-куках або JWT з refresh-ротацією.
  **2FA (TOTP) обов'язкове** для операцій виведення й великих переказів.
- **Авторизація:** перевірка `capabilities` + власності ресурсу на кожному ендпоінті
  (не в UI). Централізований guard, не копіпаста.
- **Rate limiting** на auth і на грошові ендпоінти (`@fastify/rate-limit`).
- **Валідація** — Zod-схеми на межі, спільні між клієнтом і сервером.
- **Аудит** — розширити наявний `audit_log`: хто, що, звідки (IP, user-agent), коли.
  Для фінансових дій — обов'язково.
- **Reconciliation job** — щодня перевіряє: Σ всіх проводок по кожній валюті = 0;
  `account_balances` = SUM(ledger_entries). Розбіжність → алерт, а не мовчазна робота.
- **Ліміти:** мінімальні/максимальні суми, добові ліміти, «нова заявка не частіше
  ніж раз на N годин» — захист від спаму і від помилок.
- **Soft delete** для всього фінансового. Нічого не видаляється фізично.

## 10. Фази реалізації

Кожна фаза — робочий продукт, не «півсистеми».

**Ф0 — Фундамент (найкритичніше)**
Auth + `capabilities`. Реєстр з подвійним записом: `accounts`, `transactions`,
`ledger_entries`. Гаманці. Тести на інваріант «сума = 0». Адмінське поповнення.
*Готово коли:* можна створити двох користувачів, нарахувати одному кошти, і баланс
рахується з проводок.

**Ф1 — Рух коштів + комісії**
Перекази з коментарями. `fee_policies` і розрахунок комісії в тій самій транзакції.
Історія транзакцій з фільтрами. Ідемпотентність.
*Готово коли:* переказ між користувачами працює, комісія осідає на `platform_fee`,
подвійний сабміт не дублює.

**Ф2 — Валюти**
`HardcodedRateProvider`, quote-lock, конвертація. Мультивалютні гаманці. Спред.
*Готово коли:* конвертація створює 4 збалансовані проводки, курс зафіксований у quote.

**Ф3 — Бізнес-профіль**
Реєстрація як бізнес, каси, стартовий капітал, дашборд P&L (перенесений `engine.js`).
*Готово коли:* бізнес бачить свою чисту вартість і P&L проти стартового капіталу.

**Ф4 — Позики (серце продукту)**
Заявки, маркетплейс, ескроу-холди, синдиковане фінансування, видача, графік,
нарахування %, погашення, розподіл між інвесторами з `interest_share`-комісією.
*Готово коли:* повний цикл заявка → фінансування двома інвесторами → видача →
погашення → закриття, і сума виплат обом інвесторам + комісія точно дорівнює
сплаченому бізнесом.

**Ф5 — Рейтинг і аналітика**
Скоринг бізнесу, статистика інвестора, `balance_snapshots`, графіки, експорт.

**Ф6 — Зрілість**
Прострочки й дефолти (D2 знімається), реструктуризація, сповіщення, 2FA,
admin-панель, reconciliation-job.

**Ф7 — Реальні курси**
Підключення твого API (`{CODE, BID, SELL}`) як другого провайдера. Має бути
заміною конфігу, не коду — це і буде перевіркою, що абстракція з §3.3 правильна.

## 11. Ідеї на розширення (не для MVP, але варто закласти)

**Продуктові**
- **Авто-інвестування** — інвестор задає правила (валюта, мін. ставка, мін. рейтинг,
  макс. на одну позику), система розкладає кошти сама. Це те, що робить платформу
  живою — інвестору не треба сидіти й обирати.
- **Диверсифікація за замовчуванням** — попередження «70% портфеля в одному бізнесі».
- **Вторинний ринок** — інвестор продає свою частку в позиці іншому інвестору
  (вихід до строку). Дуже підвищує привабливість.
- **Револьверна кредитна лінія** — бізнес бере/повертає в межах ліміту, платить
  тільки за використані дні. Це найближче до «користування грошима».
- **Резервний фонд** — частина комісії йде в пул, який частково покриває дефолти.
  Сильний фактор довіри.
- **Ескроу під конкретну ціль** — кошти йдуть не на гаманець, а прямо постачальнику.
- **Групові/сімейні рахунки**, спільні цілі.
- **Реферальна програма.**

**UX**
- Онбординг-калькулятор: «вкладу 10 000 під 18% на 6 міс → отримаю X»
- Сторінка бізнесу як публічний профіль: історія, рейтинг, фото, опис
- Симуляція «що якщо» перед підтвердженням будь-якої операції
- Сповіщення: платіж отримано, заявка зібралась, наближається дата платежу,
  прострочка (email + in-app, пізніше Telegram-бот)
- Темна тема, мобільний PWA

**Технічні**
- Event sourcing / outbox для інтеграцій і сповіщень
- Feature flags для поетапного розкату
- Sandbox-режим з фейковими грошима (демо без ризику)
- Публічна статистика платформи (обсяг, середня ставка, % дефолтів) — довіра
- Повний CSV/PDF-експорт для податкової

## Додаток А. Успадкована формула P&L

Збережено з `APP_CALC.md` (початковий Excel `debt calculation.xlsx` у репозиторії
відсутній). Це та математика, яку реалізує дашборд бізнесу (§5) — тепер поверх
реєстру, а не ручного вводу.

```
1. Середній курс валюти        = (BID + SELL) / 2        // лише для звітності
2. Борг у валюті X (сума)      = Σ борг усіх контрагентів у X
3. Борг у грн                  = Σ (борг у X × середній курс X)
4. Обігові кошти в грн         = Σ (залишок у X × середній курс X) + готівка UAH
5. Чисті обігові кошти         = (4) − (3)
6. Загальний підсумок, грн     = (5) + Σ каси
7. Загальний підсумок, USD     = (6) / середній курс USD
8. Прибуток                    = (7) − стартовий капітал USD
```

Дві помилки оригіналу, які **не відтворюємо**:
- конвертація боргу бралася з рядка однієї людини замість суми по валюті
  (PLN мовчки недораховувався) — тепер конвертація завжди від сумарного боргу,
  одна функція, покрита тестами;
- порожні клітинки й пробіли підсумовувалися як числа — тепер валідація на межі,
  відсутнє значення це явний `0`.
